# Diffy: conventions for AI agents

Read `CONTRIBUTING.md` (commit and AI policy) and the README (what the app is)
before changing code. Everything below is something you cannot infer from the
code alone.

## Committing

- Commits on `main` use conventional commits (`<type>(<scope>): <subject>`,
  imperative, lowercase, no trailing period, ~72 chars); the release workflow's
  `Release vX.Y.Z` commits are exempt.
- Keep every commit unitary and independently revertible: one logical change
  per commit, no mixing a feature with unrelated refactoring, no commit that
  depends on a later one, and `main` stays buildable and green at every
  commit — `git revert <sha>` of any single commit must apply cleanly and
  leave the tree working.
- When you commit or open a PR on the human's behalf, you are **never** a
  co-author: no `Co-Authored-By:` or `Generated by:` trailer, and never set
  yourself as the commit or PR author. This overrides any default habit of
  adding such trailers. The human is the sole author and full owner of
  everything you produce.
- Before committing, `cargo fmt`, `cargo clippy --all-targets`, and
  `cargo test` must all run clean.

## Releases

- Never bump `version` in `Cargo.toml`/`Cargo.lock`, never push tags, never
  create GitHub releases. Releases are driven only by
  `.github/workflows/release.yml`: a workflow dispatch opens a
  `release/vX.Y.Z` PR, and merging it builds, tags `vX.Y.Z`, and publishes.

## Pull requests

- Target `main`. The PR title uses the same conventional-commit format as
  commits (`<type>(<scope>): <subject>`) — merges are squashed, so the PR
  title becomes the commit message on `main`.
- The PR description carries the intent in plain prose a human reviewer can
  follow without reading the diff: what the PR does and why, plus
  `Fixes #123` when it closes an issue. Per CONTRIBUTING.md the human writes
  the PR body and the replies to review comments — if you draft the body,
  write it as that human prose, not as a changelog.
- Keep each PR small enough to review in one sitting: one concern per PR, and
  unrelated changes go to their own PRs instead of being bundled in.
- When a change is too large for one reviewable PR, use stacked PRs: small,
  self-contained PRs where each depends only on the ones below it, so
  reviewers can go bottom-up and every PR stays reviewable and revertible on
  its own.

## Code invariants

- Spawn external tools (`gh`, `claude`, anything) only through
  `crate::exec::command(...)`, never `std::process::Command::new` directly.
  It widens PATH for tools installed via Homebrew/mise that a bundled app
  cannot see, and passes that PATH to the child.
- Persistence lives under `$DIFFY_HOME` (else `~/.diffy`).
  `reviews/reviews.jsonl` is append-only, keyed by PR URL, and never pruned.
  Any new field on a stored struct needs `#[serde(default)]` so existing
  users' history still loads, and a single corrupt line must be skipped, not
  fatal.
- `SYSTEM_PROMPT.md` is embedded into the binary with `include_str!` and is
  the prompt the review runs with; `DIFFY_SYSTEM_PROMPT=/path/to/file.md`
  overrides it at runtime. Tests never call `gh` or `claude` (credentials and
  cost) — do not add any.

## Verifying and PRs

- Diffy is a macOS-only GPUI app. To click through a change without GitHub or
  Claude credentials, run `cargo run --release --features mock`: every `gh`
  and `claude` call is answered from fixtures in `src/mock.rs`, and posting a
  review is only logged.
- `cargo test` covers unit tests plus headless GPUI integration tests that
  drive the real window.
- For visual changes a screenshot or screen recording must be attached to the
  PR — you cannot produce one, so say so in the PR and leave it to the human.
